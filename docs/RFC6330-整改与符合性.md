# 2026-11-18 审核意见整改与标准符合性

邮件认可丢包恢复用途、MoonBit 核心实现和技术深度，驳回原因是申报范围排除完整 RFC 6330 参数支持、最终目标未覆盖完整标准符合性。本次修订把完整符合性列为最终目标，同时保留当前证据的实际边界。邮件允许在 **2026 年 11 月 30 日前**修改报名表并提交新信息，此时间以本次邮件为准。

标准依据：[RFC 6330](https://www.rfc-editor.org/rfc/rfc6330.html)；对象最大长度采用已确认的 [技术勘误 5548](https://www.rfc-editor.org/errata/eid5548)。

## 标准覆盖矩阵

| 条款 | 旧版情况 | 本轮实现 | 证据及剩余工作 |
|---|---|---|---|
| 5.6 参数表 | 只到 K′=257 | 全部 477 行，到 56,403，二分选取 K′ | 测试逐个检查 K=1..56403 的最小扩展；生成数据独立计数 |
| 3.3 OTI | F 为小对象，T≤4096，Z≤16，N=Al=1 | TransmissionInfo 支持完整字段宽度及合法性组合 | 含 F>2³² 与最大合法 F 的无分配往返测试 |
| 勘误 5548 | 未纳入 | 最大 F 使用 942,574,504,275 | 以 RFC 勘误和固定版 Rust 实现为依据；Z 最大 255 |
| 4.4.1.2 源块与子块 | 仅连续单子块 | Int64 对象偏移、Partition、Al 对齐、交织与逆变换 | 非均匀分块、尾部补零及 Al=4 测试；独立 Python 布局配合 Rust 编解码验证 3 组对象、9 个源块 |
| 4.4.2 聚合符号 | 只接收单符号包 | EncodingPacket 接收多个连续 ESI，验证范围及源/修复边界 | 修复专用聚合恢复、整包冲突回滚和源块路由测试 |
| 5.3 编码 | 小范围密集矩阵 | StandardBlockEncoder 稀疏预编码与失活求解 | 小规模逐字节比对旧路径；新增规模独立 Rust 检查见报告 |
| 5.4 解码 | K≤256 密集/在线消元 | StandardBlockDecoder 分离稀疏消元与失活残余密集求解 | K=4096 和最大 K=56403 已实际恢复；旧流式接口仍属于小块路径 |
| 5.8 解码恢复要求 | 未列为最终目标 | 已列为最终验收门槛 | **尚未完成全表恢复性质验证，不能标注已通过该条款** |
| 6 完整性 | 提醒上层验证 | 沿用对象摘要/签名由上层验证的边界 | CRC32C 检查点不是认证机制 |

## 这次确实改变了什么

新路径不再分配完整 L×L 矩阵。先建立稀疏 LDPC、HDPC 和 LT 约束，按最小活跃度选主元，将其他列转为失活列；使用静态列关联查找受影响行，只对失活残余建立密集矩阵。完整参数表不会自动证明算法正确，因此另有稀疏/密集约束逐项比较、编码字节比较、秩不足与不一致方程测试。

`ExecutionLimits` 分别限制中间符号元素、稀疏系数项和残余密集项。默认上限为 16,777,216 个符号元素、8,388,608 个稀疏系数、16,777,216 个密集系数，允许调用者调整。它们是元素预算，不是进程 RSS 保证。合法 OTI 可以被解析而因实际执行预算不足被拒绝；错误分类为 ResourceLimit，不伪装成标准参数非法。

最大 K 的验证显式把稀疏系数预算设为 33,554,432；默认预算会拒绝该验证轨迹。最大块只收齐全部系统符号时直接恢复，额外方程仍进入求解器检查一致性，不能用快速路径跳过附加信息。

大型对象按块交给调用者读写，通过 `block_layout` 的 Int64 偏移定位原对象，避免要求整份接近 TB 的对象装入一条 Bytes。子块交织由 `source_symbol` 实现，恢复后调用 `reassemble_block`。本轮尚未提供完整文件系统对象传输服务。

## 如何复核

```powershell
moon check --deny-warn
moon test --release --deny-warn
moon test --release --deny-warn --target wasm-gc
moon test --release --deny-warn --target js
moon run examples/standard --release
python tools/verify_standard.py
python tools/verify_layout.py
python tools/check.py
python tools/source_lines.py
```

`verify_standard.py` 使用固定 Rust raptorq 2.0.0，检查 K=257、1024、4096、56403：丢弃 ESI 为 10 的倍数的源符号，接收 ceil(K/10)+16 个修复符号；逐字节核对修复符号，并双向恢复原数据。Linux 先按 README 安装参考包；Windows 通过 WSL 运行该参考包。该脚本输出当前机器上的耗时，不以固定毫秒阈值作为符合性判据。最大块运行耗时与内存明显高于小块。

`verify_layout.py` 在独立 Python 中按 RFC 划分并交织对象，再交给 Rust 单块编解码器。它生成 Rust→MoonBit 测试向量，并让 Rust 接收 MoonBit 实际输出、逆交织及核对原对象。覆盖 N=2/3/7、Al=1/2/4、Z=2/3/4，包括零宽子块。该组合不是 Rust 自定义 OTI 对象接口验证，报告保留这一区别。

## 完整符合性仍需的证据

RFC 5.8 的要求覆盖参数表全部 K′，并约束接收 K′、K′+1、K′+2 个随机 ESI 时的恢复失败率，阈值分别为 1/100、1/10,000、1/1,000,000。少量无失败运行不足以证明后两个阈值。后续必须明确抽样方法、样本数、随机种子、ESI 分布、置信界和适用 K′，并结合满秩方程求解的正确性证据，不能把少数参数点互操作结果扩写成统计认证。

还应扩充非默认 N、Al、Z 的独立端到端互操作向量、随机 ESI 与边界 ESI 覆盖，并验证各后端大块执行的资源行为。标准要求、功能实现、测试覆盖和已发布版本需要在报告中分别记录。完整证据补齐前，申报书应说明“以完整标准符合性为最终目标”，不能写“已经完成完整标准认证”。
