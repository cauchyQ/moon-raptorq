# 对照方法与结果解读

## 比较谁，为什么

MoonBit 生态已经有纠删码库。MoonErasure 0.3.0 是实际发布的 Reed–Solomon 实现，MoonRecoder 0.1.1 是 GF(256) 随机线性网络编码实现；本项目不能宣称首次给 MoonBit 提供纠删码。

| 能力 | MoonRaptorQ 本轮 | MoonErasure 0.3.0 | MoonRecoder 0.1.1 |
| --- | --- | --- | --- |
| 核心 | RFC 6330 RaptorQ | 系统式 Reed–Solomon | 显式系数 GF(256) RLNC |
| 修复符号 | 在 24 位 ESI 范围内按需生成 | 预先配置 data/parity 总数≤256 | 生成随机系数包，也支持反馈修复与中继重编码 |
| 本轮范围 | 每块 K≤256，Z≤16，T≤4096 | data/parity 各 1～255，总数≤256 | 每代 K≤64，T≤4096 |
| 恢复保证 | 取决于独立秩 | 足够数量的有效不同分片可恢复 | 取决于独立秩 |
| 传输与保护 | 标准 4 字节 FEC ID，OTI 外置；无 CRC/认证 | 自有 envelope、manifest、CRC32C | 自有含系数的报文与 CRC |
| 独立互操作证据 | 与 Rust raptorq 2.0.0 交换符号 | 上游自有验证，非本轮工作 | 上游自有验证，非本轮工作 |

上表依据本次下载的实际发布源码和接口。上游会更新，版本号不可省略。本库的增量消元并非独创，相邻 RLNC 库也提供它。主要区别是标准 RaptorQ 符号的确定性生成和互操作，以及相应的预编码实现。

## 实验控制

`lab/scenarios.mbt` 为四种编解码路径生成同一组原始字节与收包序列。组播为 K=32、T=128、6 个接收方、20% 独立丢包；设备场景 K=64、T=128，丢失连续 24 包并叠加 10% 随机丢包；边缘场景 K=64、T=64、25% 丢包、倒序与重复。这里只比较各库共同支持的参数范围，不用 RLNC 不支持的 K=128 强行制造失败。

所有算法发送同样数量的符号，先系统符号后冗余。未模拟接收方反馈与自适应发送，所以没有测试 MoonRecoder 的反馈修复优势，也没有评估 Reed–Solomon 在存储修复中的完整能力。不能据此给算法作总排名。

编码时间包含库建立、符号生成及报文序列化。接收时间包含必要的元数据读取、解析、去重或入基和恢复。MoonErasure 拒绝重复索引，适配器先去重，耗时与实际收到的重复字节仍计入。编码在同一组播轮次中只统计一次。预热一轮，实测五轮，原始数据完整保留。

本库未附加 CRC，其他库报文自带元数据和校验。发送字节的差异同时反映了协议功能差异，不能直接写成“相同保护强度下更省带宽”。进程启动、编译、网络排队、真实带宽、摘要和签名验证均不在计时内。

## 如何读结果

结果见 [MEASUREMENTS](../reports/MEASUREMENTS.md) 与 [SCALING](../reports/SCALING.md)。本轮本库在三场景、两后端的测试轨迹均精确恢复；部分规模下耗时优于邻近实现，部分场景没有优势。流式接口的价值是逐包秩进度和避免重复建立系统，单次最后统一解码时并不必然更快。

MoonRecoder 在设备场景的五个丢包种子中有三个停在秩 62 或 63，Wasm 与 JS 可复现。编码系数种子固定为 20261117，丢包种子为 20261118～20261120，实际保留 75～77 个不同包。原始行见 [nonrecoveries.json](../reports/nonrecoveries.json)。这只说明该版本在这组系数和轨迹下欠秩；没有证明 RLNC 普遍失败，也没有定位上游缺陷。本轮未运行其反馈修复来补足缺失秩。

192 次仅修复符号试验记录固定种子下在 K、K+1、K+2、K+4、K+8 个符号时的秩。本轮这些样本在 K 包时均恢复；样本数有限，不能替代 RFC 的概率分析，更不能宣称任意 K 包保证恢复。

## 互操作边界

12 个 K 值覆盖小 K 补齐、表项边界与 K=256，T=8。Rust 生成的 834 个标准包与 MoonBit 输出逐字节核对；两方向各自丢掉部分源符号后精确恢复。另有两个多块对象，独立划分后逐块用 Rust 验证符号与恢复，再核对完整对象。

这不是全参数的互操作证明。高 ESI、T=4096、多块预算和全部 K 的系统性测试由本库的确定性/性质测试覆盖；Rust Python API 未暴露高 ESI 或任意多块 OTI 配置，因此这些项目没有被写成独立完整对象接口验证。参考库 1.8.0 的修复报文编号行为与 2.0.0 不同，本轮固定使用 2.0.0，脚本会检查版本，避免误用旧环境。
